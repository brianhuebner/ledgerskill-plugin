# Plugin Plan: Grill-First Accounting Skills

**Status:** Draft v0.3 · **Date:** October 6, 2026
**Changes from v0.2:** Adds the data contract vocabulary (section 8): fixed slots for grain, keys, mapping and dimensions that every branch file uses. Round 3 of the question tree now fills those slots, and the grill ends with a contract read-back.

---

## 1. The idea in one paragraph

An accountant, bookkeeper or controller in any field should be able to start with **one workflow, one file, and one command**. They type `/grill-books`, drop in a transaction file, and answer a short series of questions. Claude reads the file for facts, asks the person only for decisions, and writes the durable answers into a plain-text `BOOKS-CONTEXT.md`. The grill ends by writing a **branch**: a reusable procedure filed under the **format skill** for the transaction type it imports as (e.g. the `line-of-credit-paydown` branch of the `journal-entry` skill). Nothing has to be configured first.

The plugin is a universal starting point. It knows accounting and import formats, but it knows nothing about *this* business until the grill teaches it.

---

## 2. Design principles

1. **Start-up friction is the enemy.** The first session must produce something useful within about 15 minutes, with no setup step, no config file, and no vocabulary to learn.
2. **Facts are Claude's job. Decisions are the user's.** Never ask the user something the file can answer.
3. **Every question comes with a recommended answer.** The user should be able to accept most answers with a single "yes."
4. **Write it down the moment it's decided.** Durable answers go into `BOOKS-CONTEXT.md` right away.
5. **Files are created lazily.** Nothing is written until there's something real to put in it.
6. **Arithmetic is never done in the model's head.** Profiling, aggregation, footing, tie-out and validation run as deterministic scripts.
7. **Every output is traceable** back to the exact source rows behind it.
8. **One skill per import format, one branch per workflow.** Every generated skill follows `BRANCHED-SKILL-STANDARD.md`, and the standard's §7 audit runs on every create or edit.
9. **Routing is decided by data, not by names.** A branch is selected from observable facts in the source file, and the selection is declared before any output.
10. **Works in the Claude app, not just Claude Code.** No feature depends on hooks.

## 3. The minimum first session

| Piece | What it is |
|---|---|
| One command | `/grill-books` |
| One file | Any transaction export: Stripe, Square, bank CSV, loan statement, payroll register, AP aging |
| One outcome | A first branch inside a format skill, a starter `BOOKS-CONTEXT.md`, and (optionally) a first import-ready file with provenance |

### The first-session flow

```
User: /grill-books  [attaches chase_loc_statement_sep.csv]

1. Profile   → Claude runs profile.py. Reports facts in 8 lines or fewer.
2. Round 1   → Purpose: what system, what period, what it must tie to,
               and what it will be imported as (Journal Entry, Deposit, Bill…).
3. Round 2+  → Branch questions unlocked by Round 1 and the profile.
               Includes: "What fact in the data tells this apart from
               similar transactions?" → becomes the decision-table row.
4. Write     → Durable answers → BOOKS-CONTEXT.md as they're settled.
               Branch answers → references/<branch>.md.
5. Audit     → Standard §7 audit runs on the new or edited format skill.
6. Confirm   → Claude summarizes the shared understanding. User confirms.
7. Offer     → "Want me to run it now and produce the import file?"
```

The first grill quietly does setup as a side effect: it creates `BOOKS-CONTEXT.md` on the first durable answer and the format skill on the first branch. `/setup-books` exists for people who prefer configuring up front, but is never a prerequisite.

## 4. Two kinds of skills

The plugin has two layers, and they must not be confused.

| Layer | Who writes it | Where it lives | Examples |
|---|---|---|---|
| **Engine skills** | Ship with the plugin | The plugin | `grill-books`, `grilling`, `source-profiling`, `add-branch`, `audit-skill` |
| **Format skills** | Generated by the grill, owned by the user | The user's books folder | `journal-entry`, `bank-deposit`, `bill`, `exception-report` |

Engine skills teach Claude *how to build and run* accounting skills. Format skills hold *this business's* procedures.

### Engine skills

User-invoked skills orchestrate. Model-invoked skills hold the reusable discipline. A user-invoked skill may call model-invoked skills but never another user-invoked one.

| Skill | Type | Purpose |
|---|---|---|
| `grill-books` | User-invoked | Entry point. Calls `source-profiling` → `grilling`, with `books-context` active throughout, then `add-branch`. |
| `run-branch` | User-invoked | Runs a format skill on a new period's file. Produces the import file + provenance workbook. |
| `audit-skill` | User-invoked | Runs the standard's §7 audit on a format skill on demand. |
| `setup-books` | User-invoked | Optional up-front configuration. |
| `grilling` | Model-invoked | Interview engine: decision tree, rounds, recommended answers, accounting question bank. |
| `source-profiling` | Model-invoked | Runs `scripts/profile.py` and reports **facts only**. |
| `books-context` | Model-invoked | Reads, challenges and updates `BOOKS-CONTEXT.md`. |
| `add-branch` | Model-invoked | Writes a branch file, adds its decision-table row, creates the format skill if absent, then runs the §7 audit. Contains `BRANCHED-SKILL-STANDARD.md`. |
| `provenance-output` | Model-invoked | The output contract (section 12) + `scripts/tieout.py`. |
| `policy-memo` | Model-invoked | Records accounting policy decisions that pass the three-part test. |

### Frontmatter pattern

```yaml
# User-invoked: only runs when typed
---
name: grill-books
description: Interview the user about one accounting workflow and one source file until every decision is settled.
disable-model-invocation: true
---
Call the Skill tool for "source-profiling", then "grilling", with "books-context" active throughout. When the user confirms, call "add-branch".
```

Descriptions say **when** to use the skill, never what it does step by step.

## 5. Format skills and branches

### The model

- A **format skill** = one transaction type that can be imported into the ledger with an import tool (SaaSAnt Transactions for QuickBooks Online, or an IIF file for QuickBooks Desktop). The format fixes the **output shape**: the import template's columns, required fields and validation rules.
- A **branch** = one specific workflow that produces that format. Branches share the template, the balance rules and the validation script, but differ in logic: which accounts move, which signs, which sequence.

This maps exactly onto the standard's §1 scope test: branches share a domain, a data model and a validation rule set, and differ in logic.

### Format catalog (starting set)

| Format skill | Import type | Example branches |
|---|---|---|
| `journal-entry` | Journal Entry | `stripe-payout-settlement`, `line-of-credit-draw`, `line-of-credit-paydown`, `payroll-accrual`, `monthly-depreciation` |
| `bank-deposit` | Deposit | `square-daily-batch`, `check-deposit-batch` |
| `expense` | Expense / Check | `credit-card-statement`, `reimbursement-batch` |
| `bill` | Bill | `vendor-invoice-batch`, `recurring-rent` |
| `invoice` | Invoice | `monthly-retainer-billing`, `milestone-billing` |
| `sales-receipt` | Sales Receipt | `pos-daily-summary` |
| `exception-report` | None (review output, not an import) | `timesheet-review`, `dispute-review`, `duplicate-vendor-check` |

`exception-report` covers workflows whose result is a list of problems rather than a ledger import (timesheets, dispute checks). It follows the same branched shape; its "template" is the exceptions layout.

Formats are added lazily: a user's books folder contains only the format skills their grills have created.

### Format skill layout (per the standard §2)

```
journal-entry/
├── SKILL.md                         # router + invariants ONLY
├── references/
│   ├── stripe-payout-settlement.md  # one file per branch
│   ├── line-of-credit-draw.md
│   ├── line-of-credit-paydown.md
│   └── import-columns.md            # shared: SaaSAnt/IIF column spec
├── scripts/
│   └── validate.py                  # balance, accounts exist, required columns
└── assets/
    ├── saasant-journal-template.csv
    └── journal-entry.iif
```

### Example router (`journal-entry/SKILL.md`)

```markdown
---
name: journal-entry
description: Use when source data must become a Journal Entry import file for
  the ledger. Branches: stripe-payout-settlement, line-of-credit-draw,
  line-of-credit-paydown. Not for deposits, bills, invoices or expenses
  (separate format skills), and not for review-only exception lists.
---

Domain: transactions imported to the ledger as balanced Journal Entries.

## Branches
- stripe-payout-settlement: source is a processor payout report.
- line-of-credit-draw: loan principal balance increases.
- line-of-credit-paydown: loan principal balance decreases.

## Routing
| Observable input | Branch |
|---|---|
| Rows carry a payout ID; types include charge/fee/refund | stripe-payout-settlement |
| Lender statement or bank line; principal balance change > 0 | line-of-credit-draw |
| Lender statement or bank line; principal balance change < 0 | line-of-credit-paydown |

Ambiguous: a bank debit to the lender with no statement attached.
Ask: "Does this payment reduce principal, or is any of it interest or fees?"

Before any output, declare:
`Branch: <name>. Basis: <fact from the routing table>.`
Then echo the grain line (section 8), read references/<branch>.md in full and follow it.

## Invariants
- Every entry balances to $0.00. Rounding: sum, then round to cents.
- Only accounts in CHART-OF-ACCOUNTS.csv. A missing account is a question.
- Every dimension column is in the line key. An unmapped category value stops the run.
- Output uses assets/saasant-journal-template.csv columns exactly.
- Run scripts/validate.py on every result.
```

Note how branch names anchor on the direction of the obligation (`draw` vs. `paydown`), as the standard's §5 requires, rather than differing by a function word.

### Example branch file (`references/line-of-credit-paydown.md`)

```markdown
# line-of-credit-paydown

Also called: LOC payment, loan payoff, principal payment.

## Source
Lender statement or bank line; principal balance change < 0.

## Lines
| Line | Account | Debit | Credit |
|---|---|---|---|
| 1 | 2300 Line of Credit (principal) | principal portion | |
| 2 | 7100 Interest Expense | interest portion | |
| 3 | 1000 Operating Checking | | total payment |

## Rules
- Principal and interest split comes from the lender statement, never estimated.
- No statement → stop and ask for it.

## Example
[one worked example]

Run scripts/validate.py.
```

### Limits from the standard

- **Seven branches per format skill.** At eight, split the domain (e.g. `journal-entry` → `journal-entry-financing` and `journal-entry-revenue`). `add-branch` enforces this and proposes the split.
- **A parameter is not a branch.** Two loans with the same logic but different accounts are one branch with an account parameter, not two branches.
- **Renaming a branch touches exactly three strings:** description, routing table, filename.

## 6. Facts vs. decisions

### Facts: `source-profiling` reads these from the file

| Fact | Why it matters |
|---|---|
| Columns, data types, row count | Basic shape |
| Date range and timezone | Period cut-off |
| **Grain**: what one row represents | Determines every aggregation |
| Candidate unique IDs | Provenance and de-duplication |
| Distinct values of type/category columns | Each value may become a branch question |
| Sign convention | Prevents doubled or flipped amounts; feeds routing |
| Direction of balance change | Primary routing input (draw vs. paydown) |
| Currency | Conversion questions |
| Column totals, by type | Starting control totals |
| Internal consistency (net = gross − fee) | Early error detection |
| Blank or malformed values | Exceptions before mapping |

### Decisions: `grilling` asks the user these

| Decision | Typical recommended answer |
|---|---|
| What will this be imported as? (format skill) | Inferred from the destination; Journal Entry by default |
| What business event does each row type represent? | Inferred from type name |
| **What observable fact distinguishes this branch from its siblings?** | Proposed from the profile (sign, document type, payout ID) |
| Cash or accrual basis? | Accrual if both transaction and settlement dates exist |
| Which date drives recognition? | Transaction date for revenue; settlement date for cash |
| Which account does each line hit? | Proposed from `CHART-OF-ACCOUNTS.csv` |
| Summary grain (one entry per what)? | Per payout, per statement, per pay period |
| What control total must the output tie to? | Bank deposit, lender statement, payroll register |
| Rounding tolerance? | $0.00 per entry |
| Who reviews and approves? | The person running the grill |

## 7. The universal question tree

The grill works in rounds. Each round asks every question whose prerequisites are settled, numbered, with a recommended answer.

### Round 1: purpose (always asked)

1. **What is this file?** *(Recommended from the profile.)*
2. **What period does it cover, and is it complete?**
3. **What will you import this as?** Journal Entry · Deposit · Expense · Bill · Invoice · Sales Receipt · nothing (problems list only). *(Selects or creates the format skill.)*
4. **What should the result agree with?** Bank deposits · lender statement · processor payout report · payroll register.

### Round 2: branch identity

- Does this match an **existing branch** in that format skill? (Claude runs the routing table against the profile and proposes one.) If yes, the grill switches to edge cases only.
- If no: **what is this workflow called** (proposed name, checked against standard §5), and **what fact in the data tells it apart** from existing branches?

### Round 3: shape, mapping and dimensions

These rounds fill the data contract slots in section 8, in dependency order:

- **Shape:** scope and exclusions → measure and sign → entry key → line key → rollup.
- **Mapping:** for each category value in scope, the account and side. Every value must be mapped or excluded.
- **Dimensions:** for each candidate dimension column the profile found (low-cardinality text such as `location`), whether it goes to the ledger, which field (Class or Location), the value mapping, and the blank rule.
- Edge cases the profile found: negative groups, reversals, partial amounts, blanks.

When the user's answer conflicts with the data, the grill says so with the numbers: *"You said group by location, but 2 rows have no location, totaling $305.80. Where do they go?"*

### Round 4: control and sign-off

- Offset line, control total, tolerance and reviewer.
- **Contract read-back:** Claude reads the filled contract back slot by slot. The branch is written only after the user confirms it.

The session ends only when no open branches of the question tree remain.

## 8. Data contract vocabulary

When the grill ends, the decisions are written into fixed, named slots, not prose. Every branch uses the same slots and the same terms, with exact column names and values from the file, so the model has nothing to interpret. This applies two rules: the branched standard's "one term per concept, no undefined terms," and the `writing-skills` finding that omissions are fixed by required slots and wrong-shaped output by a positive description of the right shape.

### Terms

Defined once in `references/data-contract.md` (shipped by the engine, copied into every format skill).

| Term | Definition | Example |
|---|---|---|
| **Source grain** | What one row of the source file represents | One Stripe balance transaction |
| **Row key** | Column(s) that uniquely identify a source row | `id` |
| **Scope** | Which source rows this branch uses | `type` in (`charge`, `refund`, `stripe_fee`) |
| **Exclusion** | Rows in the file but out of scope, each with a reason; still counted | `type` = `payout`: posted by `bank-deposit` |
| **Measure** | The numeric column that is totaled, and its sign convention | `net`; positive increases Stripe balance |
| **Entry key** | Column(s) whose distinct values make one entry | `payout_id` |
| **Line key** | Column(s) whose distinct values make one line within an entry | `reporting_category`, `location` |
| **Output grain** | What one output line represents; always entry key + line key | One line per payout × category × location |
| **Rollup** | How the measure combines within a line, and when rounding happens | Sum; round to cents after summing |
| **Category column** | The source column that decides the account | `reporting_category` |
| **Mapping** | Category value → account and side; must cover every value in scope | `charge` → 4000 Sales, credit |
| **Dimension** | A source column carried to the ledger as a tag; never changes the account | `location` → QBO Class |
| **Dimension mapping** | Source value → ledger dimension value | `LOC01` → Class "Downtown" |
| **Blank rule** | What happens when a category or dimension value is blank | Class "Unassigned" + flag |
| **Offset line** | The line that balances each entry | 1099 Stripe Clearing |
| **Control total** | The external number the output must agree with | Payout amount on the bank statement |

### Distinctions to state explicitly

These cause most silent errors, so the shared reference names them:

1. **Source grain ≠ output grain.** "Group by payout" means nothing until the source grain is stated.
2. **Category ≠ dimension.** The category column picks the account. A dimension only tags the line.
3. **Every dimension is in the line key.** Otherwise the rollup merges dimension values and the tag is lost. `validate.py` checks this.
4. **QBO Class ≠ QBO Location.** QuickBooks Online has two separate tracking fields. Which one a source column maps to is grilled once and recorded in `BOOKS-CONTEXT.md`.
5. **Excluded ≠ unmapped.** Excluded rows were left out deliberately, with a reason. An unmapped value stops the run and becomes a question. There is no catch-all "other" account.

### The contract in a branch file

Every branch file carries this section with the same slots:

```markdown
## Data contract

Source grain:  one Stripe balance transaction
Row key:       `id`
Scope:         `type` in (`charge`, `refund`, `adjustment`, `stripe_fee`)
Exclusions:    `type` = `payout` → reason: posted by bank-deposit format
Measure:       `net`; positive increases Stripe balance
Entry key:     `payout_id`
Line key:      `reporting_category`, `location`
Output grain:  one line per payout × category × location
Rollup:        sum `net`; round to cents after summing

## Mapping (category column: `reporting_category`)
| Value     | Account            | Side when positive |
|-----------|--------------------|--------------------|
| `charge`  | 4000 Sales         | Credit             |
| `refund`  | 4010 Refunds       | Credit             |
| `dispute` | 4950 Chargebacks   | Credit             |
| `fee`     | 6150 Merchant Fees | Credit             |
Unmapped value → stop and ask.

## Dimensions
| Source column | Ledger field | Mapping          | Blank rule          |
|---------------|--------------|------------------|---------------------|
| `location`    | QBO Class    | BOOKS-CONTEXT.md | "Unassigned" + flag |

Offset line:   1099 Stripe Clearing, one per entry
Control total: payout amount on bank statement, per `payout_id`
```

### Writing rules

- Column names in backticks and values quoted exactly as they appear in the file. Never "the type column."
- Every slot is filled. "None" is a valid value; a missing slot is an audit failure.
- One worked example: three or four source rows becoming output lines. It encodes grain better than any sentence.
- Where possible, the contract is written so `validate.py` reads it directly, so the instruction and the check can't drift apart.

### Contract echo at runtime

The standard's branch declaration is extended so the model restates the shape before producing anything:

```
Branch: stripe-payout-settlement. Basis: rows carry payout_id.
Grain: transaction → payout × category × location. Rows: 10 in, 2 excluded.
```

A wrong grain becomes visible before any numbers are produced.

### Where each part lives

| Part | Location |
|---|---|
| Term definitions | `references/data-contract.md` in each format skill (shipped by the engine) |
| Business-specific values (`LOC01` = "Downtown"; location → Class) | `BOOKS-CONTEXT.md` |
| The filled contract, mapping and dimensions for one workflow | `references/<branch>.md` |
| Invariants true of every branch (every dimension in line key; unmapped → stop) | Format skill `SKILL.md` |

## 9. What gets written where

| Kind of answer | Example | Where it goes |
|---|---|---|
| Durable business facts and vocabulary | "We're on accrual basis." "'Deposit' means a Stripe payout landing in Chase ••4321." | `BOOKS-CONTEXT.md` |
| The ledger's accounts | Code, name, type | `CHART-OF-ACCOUNTS.csv` |
| Policy decisions with a real trade-off | "Revenue recognized on charge date, not payout date." | `policies/NNNN-title.md` |
| How to select the branch | "Principal balance change < 0" | Format skill `SKILL.md` routing row |
| Rules true of every branch in a format | Balance, rounding, template columns | Format skill `SKILL.md` invariants |
| Lines, accounts, signs, example for one workflow | LOC paydown line table | `references/<branch>.md` |
| Import column spec shared by branches | SaaSAnt JE columns | `references/import-columns.md` |

### Test for `BOOKS-CONTEXT.md`

Write there only if **all three** are true: it will still be true next month; it applies (or will apply) to more than one branch; it's a fact or a definition, not a procedure step.

### Test for a policy memo

Write one only if **all three** are true: hard to reverse once books close on it; a reviewer would ask "why?"; there were genuine alternatives.

## 10. `BOOKS-CONTEXT.md` format

Plain text, no procedures, no period numbers. Created lazily.

```markdown
# Books Context: Acme Coffee Co.

## Entity
- Basis: Accrual · Fiscal year end: December 31
- Ledger: QuickBooks Online · Import tool: SaaSAnt Transactions
- Functional currency: USD
- Locations: Downtown (LOC01), Airport (LOC02)

## Systems that produce files
- **Stripe**: card payments. Payouts land in Chase ••4321.
- **Chase line of credit**: monthly lender statement, PDF and CSV.
- **Gusto**: payroll, semi-monthly.

## Glossary
- **Deposit**: a Stripe payout as it appears on the bank statement. Not a *charge*.
- **Paydown**: any payment that reduces line-of-credit principal.
- **Clearing account**: 1099 Stripe Settlement Clearing. Nets to zero per payout.

## Format skills in use
- journal-entry (3 branches)
- exception-report (1 branch)

## Open questions
- Are airport sales taxed at a different rate? (asked 2026-10-05)
```

During every grill, `books-context` challenges the user's language against this file: *"Your glossary defines 'paydown' as a principal reduction, but this payment is all interest. Is it really a paydown?"*

## 12. Output contract (provenance)

Every run produces two files.

**1. The import file**: exactly the format skill's template columns, ready for SaaSAnt or IIF import. Nothing else in it.

**2. The provenance workbook**, with four linked layers:

| Layer | Contents |
|---|---|
| **Detail and lineage** | Every source row: source ID, row number, branch, rule applied, account, and which import line it feeds |
| **Summary** | Import lines at the chosen grain, each with a row count, traceable to detail |
| **Tie-out** | Source total = detail total = import total = control total, with each difference named. Completeness: rows in = rows used + rows excluded with reason |
| **Run header** | Branch declaration (`Branch: … Basis: …`), source file name and hash, period, run time, skill version, reviewer |

### Rules

- The import file is always rebuilt from the detail. Nothing is computed only at summary level.
- Signs are preserved through every grouping. Negative groups flip direction; they are never `abs()`'d.
- `validate.py` (format invariants) and `tieout.py` (provenance) must both pass before the run is called done. A failure is reported, never hidden.

## 13. Customization path

| Stage | What the user does | What changes |
|---|---|---|
| **0. First grill** | One file, `/grill-books` | `BOOKS-CONTEXT.md`, chart of accounts, first format skill + branch |
| **1. First run** | Accept the run offer | First import file + provenance |
| **2. Repeat** | `/run-branch` next month | Routing selects the branch; only new edge cases are grilled |
| **3. Sibling branch** | Grill a related file (a draw after a paydown) | One new branch file + one routing row |
| **4. New format** | Grill a file that imports as something else | New format skill from its template |
| **5. Policies** | Accept policy-memo offers | Auditable decision log |
| **6. Split** | Reach eight branches in one format | `add-branch` proposes the split |
| **7. Fork** | Edit any skill directly | `audit-skill` keeps it within the standard |

Each grill should get shorter, because `BOOKS-CONTEXT.md` and existing routing tables answer more of the questions. **That falling question count is the product's core value and the metric to watch.**

## 14. Friction-reduction checklist

- [ ] No setup command required before the first grill
- [ ] User never needs to read or know the branched skill standard; the audit runs automatically
- [ ] Profile reported in 8 lines or fewer
- [ ] Round 1 has at most 4 questions
- [ ] Every question has a recommended answer
- [ ] "Use your recommendation for the rest" is always an accepted reply
- [ ] Jargon-free first round (no "branch," "router," "grain," "provenance")
- [ ] Bundled sample files so a user can try it without real data
- [ ] Works in the Claude app; no hooks required
- [ ] First import-ready file in under 15 minutes

- **Participants:** 5 per branch: bookkeepers, small-firm accountants, in-house controllers.
- **Material:** a realistic file with **8 planted errors**.
- **Control:** the same file through plain Claude with no plugin.

| Metric | Target |
|---|---|
| Time to first import-ready file | < 15 minutes |
| Questions asked in first grill | Track; should fall on later grills |
| Recommended answers accepted unchanged | > 70% |
| Planted errors caught | 8 of 8 |
| Correct rows wrongly flagged | 0–1 |
| **Routing accuracy with branch names redacted** | 100% (standard §7, check 2) |
| File imports into SaaSAnt without errors | First try |

## 16. Out of scope for v1

- Posting directly into the ledger (import files only)
- Multi-entity consolidation
- Tax return preparation
- Hooks-based enforcement
- A hosted service; everything runs in the user's folder

## 17. Open questions

1. **Chart of accounts across format skills.** The standard places shared lookups inside each skill's `references/`. The chart of accounts is shared across *all* format skills, so v0.2 keeps it at the books root (`CHART-OF-ACCOUNTS.csv`) where every `validate.py` reads it. Amend the standard to allow one cross-skill reference, or copy relevant accounts into each skill?
2. **Import tool targets.** SaaSAnt for QuickBooks Online is the v1 default; IIF applies to QuickBooks Desktop only. Ship both templates per format, or Online-first?
3. **Where the books folder lives** for Claude app users without a local file system.
4. **Format template depth.** How much of each format's `SKILL.md` and `validate.py` ships pre-written vs. generated by the first grill?
5. **Domain packs.** Ship as pre-built branches (e.g. a payroll pack adds `payroll-accrual` and `timesheet-review`) inside the same plugin or as separate installs?
6. **Prompt-only vs. scripted footing.** Matt Pocock's skills are prompt-only. This plan adds deterministic scripts for profiling, footing and tie-out because accounting has no compiler. Should the grill's evidence (the numbers it cites when challenging an answer) come from a script with a logged result, or from the model looking at the file?
7. **Machine-readable contract.** Should the data contract section be strict enough (or paired with a small YAML block) for `validate.py` to read it directly?
